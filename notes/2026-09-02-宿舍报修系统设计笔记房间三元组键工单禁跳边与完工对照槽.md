# 宿舍报修系统设计笔记：房间三元组键、工单禁跳边与完工对照槽

> 一上来锁 Spring Boot+小程序+Redis 做宿舍智能报修，两周后跨楼 301 撞号、维修员只在微信群接单、完工无对照图。先钉房间三元组键、状态禁跳边、完工对照槽，再判断一人八周能否交卷。
> 示例系统：宿舍报修系统
> tags: 宿舍报修系统, 毕业设计, 选题边界, 可行性评估, 工单状态机, Spring Boot

开题周最常见的动作是先起 Spring Boot 骨架，小程序画三个 Tab，Redis 先连上「显得完整」。宿舍报修尤其容易这样——谁不会做一张报修表单？两周后才发现 A 栋和 B 栋都有 301，名单在门禁库里导不出；维修员不打开小程序，接单全在微信群；论文状态图写了「已完工」，库里却能从「待派单」直接改过去。本稿只做一件事：**技术栈后置，先用三道闸门否决或收紧题目**。它是设计草稿和对照清单，不是可提交仓库，实现请自己写。

## 1. 三道闸门：过不了就换题

宿舍报修能不能交卷，不取决于你会不会用 Redis 缓存工单列表，而取决于下面三句话有没有书面口径。

**闸门 A：房间三元组权威键。** 报修必须落到「校区-楼栋-房间」唯一键，禁止用户手填「301」。来源只能有一个：宿管导出，或开题前你自己维护一份静态 CSV。跨楼撞号、学生能报别人的床位，后面查询和答辩都会穿帮。

**闸门 B：工单禁跳边表。** 合法迁移写成边，禁止任意 `UPDATE status`。最小闭环：待派单 → 已接单 → 维修中 → 待确认 → 已完工；未接单前允许已取消。没有禁跳表，论文里的状态图是假的。

**闸门 C：完工对照槽。** 报修至少 1 张现场图，完工至少 1 张对照图，槽位空禁止落入已完工。没有对照槽，评委问「怎么证明修完了」只能答「状态改了」。

| 闸门 | 开题必须钉死的一句话 | 否决信号（出现就换题或砍功能） |
| --- | --- | --- |
| 房间三元组键 | 唯一键来自哪份名单、谁更新、学生能否改 | 只有手填房间号；跨楼无前缀；导不出且不愿维护 CSV |
| 工单禁跳边 | 合法边列表 + 谁有权触发 | 后台可改任意状态；无人接单入口却写智能派单 |
| 完工对照槽 | 报修图与完工图最少张数、谁上传 | 纯文字报修；完工只打勾；图放微信群不入库 |

三闸过完再谈 Spring Boot、小程序、Redis。过不了，换题成本低于硬写四个空模块。

## 2. 过闸后的模块拆分与数据流

一人八周不要做智能派单算法、评价情感分析和配件库存。最小垂直切片只留四块：

1. 房间主数据（只读查询 + 导入）
2. 报修单（创建、取消、按状态查询）
3. 接单与状态迁移（维修员或宿管）
4. 证据槽（报修图、完工图元数据）

数据流：学生持登录态选房间键 → 上传报修图 → 生成待派单 → 维修员接单 → 开工 → 上传完工图请求确认 → 学生或宿管确认已完工。Redis 只承担待派单池和防重复提交，业务真相在 MySQL。

| 模块 | 八周必做 | 明确不做（写进开题「范围外」） |
| --- | --- | --- |
| 房间主数据 | CSV/SQL 导入、按楼栋检索 | 对接门禁实时同步 |
| 报修单 | 创建、取消、按状态查询 | 语音报修、GPT 分类故障 |
| 接单迁移 | 抢单或指派二选一，禁跳校验 | 路径规划、配件商城 |
| 证据槽 | 对象存储 URL + 必填校验 | 图像识别损坏程度 |
| 缓存 | 待派单列表、创建幂等键 | 用 Redis 当工单主库 |

## 3. 最小表结构（对照用，不是建库脚本）

- `room(id, campus, building, room_no)`，唯一约束 `(campus, building, room_no)`
- `ticket(id, room_id, reporter_id, type, desc, status, assignee_id, created_at)`
- `ticket_photo(id, ticket_id, kind /* report|done */, url, uploaded_by)`
- `ticket_log(id, ticket_id, from_status, to_status, actor_id, at)`

查询一律走 `room_id`，禁止再按字符串「301」过滤。`ticket_log` 是论文状态图的证据，不是装饰表。

## 4. 核心用例伪代码：创建报修并合法接单

只描述主路径，当作对照清单，不要当成可粘贴工程。

```pseudo
function createTicket(user, campus, building, roomNo, type, desc, photoUrls):
  room = RoomRepo.findUnique(campus, building, roomNo)
  if room is null: return Fail("房间键不存在，禁止手填幽灵房间")
  if user does not live in room: return Fail("只能报自己宿舍")
  if photoUrls is empty: return Fail("报修对照槽为空")
  if Redis.SET_NX("ticket:dedup:" + user.id + ":" + room.id, 30s) is false:
    return Fail("重复提交")
  t = Ticket{room, user, type, desc, status: PENDING_ASSIGN}
  save t and REPORT photos
  append log null -> PENDING_ASSIGN
  Redis.LPUSH("queue:pending", t.id)
  return t.id

function acceptTicket(worker, ticketId):
  t = lock ticket
  if not allowed(t.status, ACCEPTED): return Fail("禁跳")
  if t.assignee is not null: return Fail("已被接单")
  t.status = ACCEPTED; t.assignee = worker
  Redis.LREM("queue:pending", t.id)
  append log PENDING_ASSIGN -> ACCEPTED
  return OK
```

状态是否允许跳转，用静态边表判断，不要在 Controller 里堆 if。Java 边表示意如下（非完整项目）：

```java
Set<String> EDGES = Set.of(
  "PENDING_ASSIGN->ACCEPTED",
  "ACCEPTED->IN_PROGRESS",
  "IN_PROGRESS->WAIT_CONFIRM",
  "WAIT_CONFIRM->DONE",
  "PENDING_ASSIGN->CANCELED"
);
boolean allowed(String from, String to) {
  return EDGES.contains(from + "->" + to);
}
```

完工路径必须先检查 `kind=DONE` 的照片槽，再允许待确认 → 已完工。缺图直接失败，不要靠后台改状态救演示。

## 5. 四十分钟可行性评估

按这个顺序计时，任何一步卡死就停：

1. 向宿管确认能否拿到「校区-楼栋-房间」名单；拿不到就决定是否自己维护 CSV，并写进论文「数据来源」。
2. 在纸上画出合法状态边，删掉没有执行人的「自动完工」「智能调度」。
3. 规定报修图、完工图各至少一张，以及确认人是学生还是宿管（两人角色你一个人演示要罩得住）。
4. 用二十分钟口述主链路：选房间 → 上传图 → 接单 → 完工图 → 确认；口述卡壳说明切片太大。
5. 这才打开 IDE：Spring Boot 只提供房间查询、工单命令、状态校验三个 API；小程序只做两类角色页；Redis 只接幂等与待派单队列。

若第 1 步名单不存在且你拒绝维护主数据，换题。不要把错误房间号塞进 Redis。

## 6. 栈后置时的职责边界

Spring Boot：房间只读、工单命令、禁跳、事务写 `ticket_log`。小程序：学生报修/确认、维修员待派单与接单，不做复杂后台。Redis：`SET NX` 防重复提交、`LIST` 待派单，禁止把 status 只存在缓存。MySQL 仍是唯一事实源。闸门过完再写进开题「技术路线」，不要倒过来用技术栈定义题目。

宿舍报修看起来像 CRUD，真正否决它的是房间撞号、状态乱跳、完工无图。先把三元组键、禁跳边、对照槽写成一页说明书，再决定要不要开仓库。本文是对照清单，不是代写方案；表结构与伪代码需按学院口径自己落地。过闸做薄，不过闸换题。
